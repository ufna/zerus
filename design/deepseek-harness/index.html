Родной DeepSeek Harness как ещё один движок сессий HGS

Предлагаемый путь: запускать официальный @deepseek-ai/dsh на выбранной машине и подключать Zerus к его API. DeepSeek сохраняет свой агентный цикл, инструменты, правила доступа и историю. HGS объединяет интерфейс, машины и навигацию.

Первый адаптер реализован в HGS 1.26 / Zerus 0.17. Проверена официальная версия 0.2.0-rc.2; изучены также исходники 5badb150 с версией 0.2.1-alpha.1. В New session используется официальный dsh.

Создание, переименование, список сессий, чтение проекций и каталога моделей прошли через родной Web API.

Форк

Форк по точной границе истории создал отдельную сессию. Обычный форк пустой беседы ожидаемо отклонён: ещё нет завершённого ответа.

Результат проверки. Процесс пробы остановлен, временный профиль удалён. Реальные ответы модели, авторизация аккаунта, загрузка вложений и восстановление потоков после обрыва ещё не проверены.

API, агентный цикл, история

Один host обслуживает несколько бесед одного native-профиля. Идентичность сессии: machine + native profile/account + sessionId. Процесс host не равен сессии; закрытие Zerus не должно останавливать агента. Удалённое соединение идёт через SSH к loopback-сервису.

Что меняется в HGS

Добавить backend dsh_host рядом с текущим tmux_cli. Вынести обнаружение, запуск, отправку, отмену, инспекцию и форк за интерфейс возможностей backend. Текущие lifecycle.rs, input.rs и journal.rs привязаны к pane/PID; для dsh источник активности — состояние конкретного агента внутри host.

Нативный journal остаётся у DeepSeek. HGS хранит нормализованный индекс для поиска и компактные состояния. Переподключение восстанавливает курсор событий; повтор отправки использует тот же requestId. Подтверждение приёма сообщения не считается завершённым ответом. Переигранная история не создаёт новые уведомления.

Модель и effort: найден существенный нюанс

Штатный session.selectModel меняет выбор беседы и затем сохраняет его как default профиля. Наше обещание «только для этой сессии» с этим несовместимо. Перед включением выбора нужен небольшой адаптер в официальной системе плагинов, использующий путь выбора для конкретного агента без сохранения default, либо upstream-параметр scope. Временная установка и откат общего default создадут гонку и не подходят.

Список моделей и допустимых effort берём из native-каталога выбранного маршрута авторизации. Недоступность модели показываем явно.

Аккаунты и соединение

Accounts хранит имя и ссылку на native-профиль машины. DeepSeek account и API key — разные способы входа. Используем штатный login flow, секреты остаются у harness. Копирование всего DSH_HOME между машинами не подходит: вместе с ключами туда попадают история и секреты host.

При подключении используем штатный обмен стартового URL на cookie. Не читаем секрет подписи cookie и не подделываем авторизацию. Существующий host подключается явно; второй владелец той же истории не запускается.

Операции и границы жизненного цикла

Stop отменяет текущий ответ выбранной сессии. Pause/close должны дождаться завершения её дочерних работ и оставить историю. Остановка общего host — отдельная операция уровня машины, затрагивающая все его беседы. Она не должна скрываться за кнопкой Terminate session.

Проверяем вопросы и разрешения после переподключения: пользовательский ответ адресуется живому запросу, а не записи в истории. Группы и Pinned остаются метаданными HGS. Existing worktree передаётся как cwd; наличие форка беседы само по себе не создаёт worktree.

Как это будет выглядеть

В New session появится провайдер DeepSeek Harness с машиной, аккаунтом, папкой/worktree и группой. В сессии — привычная Activity и кнопка Open native UI. Web UI DeepSeek доступен для его специальных настроек. Терминал папки можно открыть отдельно.

Первый адаптер и дальнейшее развитие

Реализованы приватный Cordis-адаптер для официального release host, Activity, отправка/steer, изображения, вопросы/разрешения, session-only модель и effort, pause/resume, rename, goals, todo и дочерняя Activity. Native fork, расписание и глобальный поиск DeepSeek остаются в родном UI. Пункты ниже описывают полное целевое покрытие.

  1. Host и чтение: версия, явное подключение/запуск, аккаунт, сессии, история, живые состояния, native UI. Проверить Linux и macOS, переподключение и одновременное использование родного UI.
  2. Работа из Zerus: создать, отправить и steer/queue, вложения, вопросы/разрешения, отмена, модель/effort с правильной областью действия, rename и native fork. Тесты не должны останавливать соседние беседы.
  3. Полная наблюдаемость: goals с activation, планы, подагенты, фоновые задачи и расписание; общий поиск и read state. Проверить replay без ложных новых ответов и фоновые задачи после закрытия GUI.

До выпуска полноценной интеграции нужны реальные turn-тесты с настроенным аккаунтом, проверки возврата pending questions после обрыва и фиксация поддерживаемых версий API. Текущие интеграционные тесты используют официальный движок и локальную тестовую модель: история, ответы, вопросы, изоляция настроек и остановки, штатный browser cookie flow. Авторизация конкретного пользователя проверяется при его входе.
